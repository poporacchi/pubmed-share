TTSモデル解説と
商用利用ガイド

音声合成（Text-to-Speech）の方式の系譜から、2024〜2026年の代表モデル、評価の読み方、オンデバイス化、そして「商用で使えるかどうか」の判定までを一枚に整理した。2024〜2026年の実務上の分岐は、性能よりもライセンスと運用形態にある。

まず結論 ― 商用で「交渉なしに使える」もの

  • オープンウェイト：Kokoro-82M、Qwen3-TTS、CosyVoice、Chatterbox、ZONOS3-Mini、Inflect v3 は重みまで Apache-2.0／MIT でクリーン。GPT-SoVITS は依存モデルの個別確認が前提。
  • 人気でも商用不可の代表例：F5-TTS（重み CC-BY-NC）と Fish Speech 系（旧系 CC-BY-NC-SA、S2-Pro は Research License）。「人気＝商用可」ではない。
  • 商用API： ElevenLabs は有料プランのみ商用可（無料期間の出力は後から有料化しても遡及しない）。OpenAI API・Google Cloud TTS は商用可。Azure は有料ティアのみが商用グラントの対象。
  • 日本語サービス：エンジンの規約と「声（キャラクター）ごとの規約」は二重構造。エンジンが商用可でも、選んだ声が不可なら不可。
  • 声クローン：モデルのライセンスが可でも、他人の声を再現する権利は含まれない。本人の明示的・書面の同意が別途必要。

※ 本ページは技術解説であり、ライセンス解釈は法的助言ではありません。商用判断では、公開直前に各リンク先・リポジトリの条文原文を必ず再確認してください。

01方式の系譜 ― 何を解決し、何が残ったか

パイプラインの基本形は今も変わらない：テキスト正規化 → G2P（文字→音素）→ 音響モデル（音素→音響特徴）→ ボコーダ（音響特徴→波形）。各世代は「このどこを学習対象にし、どこを消したか」で理解できる。TTSの歴史は、手作業の排除と生成の確率モデル化の歴史である。

  1. ルール／フォルマント代表：Klatt 等

    声道の共鳴を規則で合成。解決：録音なしで任意の文が読めるようになった。残った課題：機械的な音質、規則の手作業が膨大。

  2. 連結合成（concatenative）代表：1990年代の商用TTS

    録音済みの音素／音節片を接続・加工する。解決：実音声なので音質自体は自然。残った課題：接続部の不連続、話者・感情の追加は再録音が必要、辞書外に弱い。

  3. 統計的パラメトリック（SPSS）代表：HMM-TTS（HTS）、Zen et al. 2009

    音響特徴の分布を HMM で学習し、パラメータから生成。解決：小データで一般化でき、話者適応も可能に。残った課題：過平滑化で「こもった」音になり、自然さの天井が低い。

  4. ニューラル波形生成代表：WaveNet（2016）

    波形サンプルを自己回帰で予測（dilated CNN）。解決：波形レベルの自然さが跳ね上がった。残った課題：サンプル単位の逐次生成で極端に遅い。テキスト条件付けは別途必要。

  5. 高速ボコーダ代表：WaveGlow、HiFi-GAN、iSTFTNet

    メルスペクトログラム→波形を GAN／flow／iSTFT で並列生成。解決：WaveNet ボコーダの速度問題を解消。現在も多くのモデルの最終段を担う。残った課題：ボコーダ単体では韻律（抑揚）は決まらない。

  6. エンドツーエンド（seq2seq）代表：Tacotron（2017）／Tacotron 2（2018）

    文字→メルスペクトログラムをアテンション付き seq2seq で学習し、WaveNet／HiFi-GAN で波形化。「text→mel→wave」が標準形になった。解決：特徴量設計の手作業を排除し、自然さが実用水準へ。残った課題：アテンション崩壊による読み飛ばし・繰り返し、自己回帰で遅い、長文に弱い。

  7. 非自己回帰（non-AR）代表：FastSpeech（2019）／FastSpeech 2

    音素の継続長（duration）を明示的に予測し length regulator で展開、並列生成。2 では pitch／energy も予測。解決：並列化で高速・頑健になり、速度／高さの制御も可能に。残った課題：duration の教師は Tacotron 等からの蒸留に依存（2 で緩和）、表現力は中間特徴の設計次第。

  8. flow／VAE 統合代表：Glow-TTS、VITS（2021）

    VAE＋normalizing flow＋敵対的学習＋確率的 duration で、テキスト→波形を単一モデルで学習。解決：音響モデルとボコーダの段差（カスケード誤差）を消した。高品質・高速で、Piper／VOICEVOX 系／Style-Bert-VITS2 の基盤になった。残った課題：学習の不安定さ、話者は基本固定（追加学習が必要）。

  9. 音声コーデック＋言語モデル代表：VALL-E（2023）、VALL-E 2、XTTS、Orpheus、Sesame CSM、Qwen3-TTS、Fish S2

    EnCodec／SoundStream 系の RVQ コーデックで音声を離散トークン化し、LLM のように次トークンを予測。第1コードブックを AR、残りを non-AR で埋める構成が原型。解決：3秒の参照音声でゼロショット声クローン（in-context learning）。大規模化（VALL-E は LibriLight 60,000時間）が効く。残った課題：逐次生成で遅延・コスト大、繰り返し／無限ループ、ハルシネーション（言っていないことを言う／読み飛ばす）、コーデックの音質天井。

  10. 拡散／Flow Matching代表：Grad-TTS、Matcha-TTS、F5-TTS（DiT＋flow matching）、E2-TTS、CosyVoice の flow 段、VoiceBox

    ノイズからメル／潜在表現を反復的に生成（拡散）、または直線軌道で輸送する（flow matching／ODE）。解決：並列生成と高い多様性・自然さの両立。音素アライメント不要な設計も可能（F5 は参照音声＋文字の in-filling 形式）。残った課題：反復ステップ数と速度のトレードオフ（蒸留で緩和）、ストリーミングは工夫が必要（CosyVoice 2 以降は causal flow matching で対応）。

  11. Speech-to-Speech／Full-duplex代表：Moshi（Kyutai, 2024）、GPT-4o Realtime／gpt-realtime、Gemini Live、Sesame CSM、NVIDIA PersonaPlex（2026）

    ASR→LLM→TTS のカスケードをやめ、音声トークンを入出力する単一モデルが「聞きながら話す」。Moshi は Mimi コーデック（12.5Hz）＋「inner monologue」テキスト流を持つ。解決：相槌・割り込み・笑い等のパラ言語情報がテキスト経由で落ちない。遅延は理論 160ms／実測約 200ms（L4、Kyutai 自己申告）。残った課題：言語・知識能力はテキスト LLM に劣りがち、評価方法が未成熟、日本語対応は商用 API 先行。TTS 単体用途には過剰。

留保：これらの世代は排他的ではなく重なっている。現行製品の多くは混成である（例：CosyVoice＝LLM＋flow matching、Qwen3-TTS＝コーデックLM＋軽量デコーダ、Kokoro＝StyleTTS 2 系＋iSTFTNet）。そして全世代を通じて「読みの正確さ（特に日本語）」「長文一貫性」「声の権利」が最後まで残った。

03商用利用ガイド ― 可否は「5層」で決まる

「商用可」は原則として「そのライセンス／プランの範囲で、生成音声を収益目的の製品・コンテンツに使える」ことを指す。再配布・ホスティング（第三者がテキストを入力する SaaS 型提供）・モデル学習への利用は、別条件になることが多い。判定は次の5層を分けて確認する。

LAYER 1

コード

MIT／Apache-2.0／AGPL 等、プログラム自体のライセンス。

LAYER 2

重み

学習済みモデルのライセンス。コードと違うことが最頻の事故原因（F5-TTS、Fish、VibeVoice）。

LAYER 3

学習データ

Emilia 等の NC 条件が重みに伝播する。

LAYER 4

声そのものの権利

参照音声・プリセット声・キャラクターの規約、話者の同意。

LAYER 5

出力音声

API のプラン別権利、透かし、クレジット表記、解約後の継続可否。

3-1. オープンウェイトの判定まとめ

第2章のカードと対応する一覧。商用プロダクトで「交渉なしに使える」のは Kokoro、Qwen3-TTS、CosyVoice、Chatterbox、ZONOS3-Mini、Inflect v3、GPT-SoVITS（依存確認前提）。Fish Audio Drama 3／fish-speech コードは Fish Audio Community License 1.0 で、年間総収益（関連会社含む）50万 USD 未満の間だけ商用ライセンスが無料で付くが、第三者が入力するホスティング型 TTS／クローンサービスは収益額にかかわらず常に別ライセンス（「Built with Fish Audio」表示等の条項あり）。

3-4. 声クローン商用の権利チェックリスト

モデルのライセンスが◎でも、他人の声を再現する権利はライセンスに含まれない。

  1. 本人の明示的・書面の同意を取る目的（学習／生成／公開）、媒体、期間、地域、収益化の有無、撤回方法を特定する。「録音データの提供＝クローン同意」ではない。主要 API も同旨を規約化：ElevenLabs は生存する個人の声を「explicit and informed consent」なしにクローン・なりすましすることを禁止し、未成年（18歳未満）の録音による声モデル作成も禁止。Professional Voice Cloning は本人の声のみで、本人が検証（voice CAPTCHA）して共有する形のみ。OpenAI のカスタム音声は同意録音のアップロードが前提。Google の Instant Custom Voice は許可制＋同意文の録音が必須。
  2. 日本の権利構造を押さえる（声そのものを守る単独の法律はない）著作権法：声そのものは対象外だが、録音された実演には著作隣接権があり、既存録音を無断で学習データに使うと侵害になりうる。パブリシティ権：最高裁ピンク・レディー事件（2012）の枠組みのもと、内閣府「AI時代の知的財産権検討会」中間とりまとめ（2024-05）は「肖像等」に声が含まれ声もパブリシティ権で保護可能と整理（法務省検討会の解釈指針も2026-08公表とされる方向で整理）。このほか「声をみだりに利用されない権利」（人格権的構成）や、声が周知・著名な商品等表示と結びつく場合の不正競争防止法の余地がある。日本俳優連合は2026-10に「音声に関する生成AI利用ガイドライン」を公表し、学習・生成・公開の全段階で実演家の事前許諾を求める立場を示した（法的拘束力はないが契約実務の参照点）。
  3. なりすまし・詐欺・政治利用は別格声紋認証の回避、本人が言っていない発言の生成、政治候補者のなりすまし（ElevenLabs は許諾があっても候補者・公職者のなりすましを禁止）、選挙攪乱、非同意の性的コンテンツは、同意書があっても許容されない用途がある。
  4. 故人の声は別途確認死後のパブリシティ権は法域で扱いが異なり、遺族感情・各サービスの禁止条項（ElevenLabs は害を生じうる／死後権利を侵害する故人クローンを禁止）を確認する。
  5. AI 生成であることの開示OpenAI は TTS 利用ポリシーとして AI 音声の明確な開示を要求。EU AI 法の透明性義務、プラットフォーム（YouTube／TikTok）の AI ラベル規約、日本の広告表示規制等が重なりうる。透かし（Chatterbox PerTh、VibeVoice）を除去して使う設計は避ける。
  6. 契約書に残す声優・ナレーターとの既存契約に AI 学習・AI 代替の可否条項があるか確認し、新規では「学習可否／生成物の利用範囲／対価／期間／撤回時の扱い」まで明記する。

04評価方法 ― 単一指標では決まらない

MOS／Elo（好み）、WER/CER（言っている内容の正しさ）、話者類似度（SIM）、RTFx／初音遅延は分けて見る。2026年9月公開の Hugging Face Open TTS Leaderboard が、オープンウェイトについては最も再現性のある自動評価である。

指標何を見るか落とし穴
MOS（ITU-T P.800 系、1〜5）／CMOS／SMOS人間リスナーの自然さ／比較／話者類似相対評価であり、聴取集合が変わると同じ音声でも値が動く（例：同一音声が「quality」質問で3.53、「naturalness」で3.21という研究報告）。ベンダーページの MOS 同士は原則比較不能
Elo／選好（Arena 型）2音声の盲検選好。TTS Arena、Artificial Analysis Provider Voice Leaderboard「好み」であって読みの正確さではない。短文・英語中心。Kokoro が TTS Arena v1 首位、Artificial Analysis では Eleven 系が上位、オープンでは Fish 系が高い等、ボードごとに順位は違う
WER／CER（ASR 書き起こし照合）言った内容が入力文と一致するか＝明瞭性・読み飛ばしの検出ASR 自体の誤りを含む。自然さ・感情は測れない
SIM（WavLM 等の話者埋め込み cosine）クローンの声の似せ具合似ている≠正しく読めている。WER とセットで見る
UTMOS／KOMOS、DNSMOS自動 MOS 予測（英語 UTMOS、韓国語 KOMOS 等）学習ドメイン外（騒音下、離散トークン系、韻律誤り）で人間評価との相関が崩れるという Interspeech 2026 等の報告がある。DNSMOS は本来ノイズ抑制評価用
Seed-TTS-Eval／CV3-Evalゼロショットクローンの標準セット（英・中が中心、WER＋SIM）日・英・中以外、特に日本語の読みはほぼ測っていない。Fish S2 の Seed-TTS WER 英0.99%／中0.54%（技術報告＝自己申告系統）等はこの文脈の数字
HF Open TTS Leaderboard（2026-09-30 公開）オープン31モデルを Qwen3-ASR 書き起こしによる WER/CER（日中韓は CER）、RTFx（H200、batch 条件明記）、TTFA、UTMOS／KOMOS、SIM で自動評価。23言語、固定声／クローン別自動指標のみで人間選好の代替ではない（主催者自身が明言）。英語デフォルトでは Kokoro が WER 1.46 で首位という結果（第三者記事による転記）

日本語の読み正確さ ― エラーは「フロントエンド」で起きる

日本語 TTS のエラーは音質ではなくフロントエンドで起きる。3層に分解できる。

LAYER 1

テキスト正規化

数字・記号・英字。「3/4」は日付か分数か、「10:30」「1日（ついたち／いちにち）」等。

LAYER 2

G2P（読み推定）

同形異音語・同音異義の逆問題：「辛い（からい／つらい）」「市場（しじょう／いちば）」「人気（にんき／ひとけ）」等。日本語には同形異音語が140以上あるとされ、辞書＋前後1〜2トークンの規則では原理的に解けない。助数詞の音便（1本=いっぽん、3本=さんぼん、1分=いっぷん）もここ。

LAYER 3

アクセント・句切れ

単語単体で正しくても、複合語・助詞接続でアクセント結合が変わる。東京式アクセントの核位置は意味差にもなる。

定量例（いずれも著者／研究側の自己評価ベンチであり、第三者再現ではない点に注意）：個人開発の読み推定モデル JRM（130M）の1268問ベンチでは、難読66問で100% vs 既存最強60.6%、独立260問で91.9% vs 61.9%。ただし拡張942問では全体77.0% vs 61.9%ながら固有名詞61.7%（同点）・数詞日付63.1%と、固有名詞と数字が最後まで残ることを示した（Zenn 記事）。松尾研系の辞書＋Transformer＋BERT 型 G2P では、数詞・助数詞100表現で CER 1.42% vs Open JTalk 16.24%、アクセント結合誤り 15.21%→6.04%（Code and DESIGN 記事が紹介）。

実務結論：「大規模多言語モデルだから日本語の読みも正しい」は成り立たない。対策はモデル選定とは別に、読み辞書登録／SSML・読みタグ／前処理でひらがな化（ただしアクセントが崩れる副作用あり）／用途固有の回帰テスト文セットを運用に組み込むこと。日本語専用の公開ベンチマークとして定評のあるものは2026年時点で存在せず（Seed／CV3 は日中韓 CER 止まり）、これが最大の空白である。自社用途では ①自前の固定テスト文で CER／目視聴取、②初音遅延と RTFx の実測、③長文（10分超）の一貫性、の3点を必ず自測する。リーダーボードは候補絞り込みに使う。

05小型・オンデバイス化 ― 勝ち筋は「non-AR」

効く条件は非自己回帰（non-AR）であること。1回の forward で波形まで出す VITS／StyleTTS 系は CPU で実時間を超える。AR コーデック LM は1秒の音声に数十〜数百ステップの逐次推論が必要で、量子化は1ステップを軽くするだけでステップ数を減らせないため CPU では不利――という整理が CPU 向け比較記事で繰り返し示されている。

ランタイムの収束：sherpa-onnx（Apache-2.0）が VITS／Piper／Matcha／Kokoro／Kitten／Pocket／Supertonic を単一 API で ONNX 実行し、デスクトップ・モバイル・WASM まで担う。Transformers.js（Kokoro）、MLX（Apple Silicon）、CoreML 変換、WebGPU（ZONOS3-Mini、Woof 移植）も実用域にある。

ブラウザ動作の実例：Kokoro（Transformers.js）、Phonon（ExecuTorch／WebGPU デモ、Apple Watch オフライン動作デモ＝Gradium 自己申告）、Woof（WebGPU、31.7MB）、ZONOS3-Mini（WebGPU、Pixel 9 で初音 <570ms＝自己申告）。

数十MB級の新顔（2026）：KittenTTS nano 約24MB、Phonon 31M 約65MB（初音28ms＝HF Leaderboard の CPU ストリーミング測定として Gradium が転記）、Woof 32〜41MB、Inflect Atom／Micro、Pocket TTS の英語小型版 1.9M〜18.2M（最大25×実時間＝README 自己申告）。ただし小型モデルはほぼ英語専用であり、日本語の数十MB級は Piper 系カスタム声か VOICEVOX 系が現実解である。

落とし穴：①日本語 G2P の JS 実装が未成熟で、ブラウザ版 Kokoro の日本語がボトルネックになった事例（GitHub Issue 報告）。②eSpeak-NG 依存は GPL-3.0 であり、組み込み配布ではライセンス伝播を確認する必要がある（Kokoro／Piper 系共通）。③「CPU で実時間」はコア数・スレッド条件依存で、ベンダー値は Apple Silicon 偏重が多い。低電力 x86／Raspberry Pi では自測必須。

06選定の観点と用途別の第一候補

見るべき観点は、自然さ／読み正確性／速度（初音遅延 TTFA と RTFx は分離する。会話用途は TTFA <300ms が目安、バッチ制作は RTFx 優先）／声クローン（必要参照長は3秒〜30分）／感情表現（指示文、タグ、exaggeration、スタイルベクトル。強い表現ほど読み誤り・不安定化が増える）／ライセンス（5層）／コスト（API 従量 $4〜160／100万字 vs 自前 GPU vs ローカル CPU。大量・定常負荷は自前、少量・高品質は API が安い）／運用（API はベンダー廃止リスク、モデル deprecate が頻発）。
